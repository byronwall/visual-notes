# CU-09 Verify property edits survive overlapping failures and navigation

**Priority:** P1 · **Evidence:** Source risk; not a demonstrated data-loss incident · **Baseline:** `25c7a864947994b8f321ceab73e6b8eae14e3107`

## Current behavior

setValues optimistically patches values, snapshots entire rows, and restores those snapshots on rejection. It does not expose pending property-write state. RowPeekPanel guards the note-body editor dirty state, which is a valuable existing safeguard, but does not await these property mutations.

## User impact and gap

An older failed request can restore a row snapshot predating a newer successful edit. A close can also happen while a property request is unresolved. This is a concrete race candidate, not proof that deployed data was lost; server patches and later revalidation may correct the display.

## Reproduce

1. In an isolated database hold edit A, commit edit B on another property of the same row, then reject A.
2. Repeat on the same property and with a rename, close/reopen and live refresh.
3. Compare UI, reload and persisted values after each resolution order.

## Likely ideal and proposed work

Use per-property/version-aware optimistic reconciliation and explicit pending/error state. Retain user drafts on failures. Extend the close/navigation contract to property edits while preserving the existing body-save guard.

## Acceptance and reassessment

- [ ] Failure of A never erases newer successful B in the UI or persistence.
- [ ] Close/reopen and reload show a truthful saved/pending/failed state.
- [ ] Retry and cancel affect only the intended edit and are idempotent.

Run R08 in the [reassessment protocol](../../../../../docs/intent/collections-usability-audit-2026-11-11/reassessment.md). Record fixed commit, browser/device, before/after screenshots and test result. A source hypothesis becoming confirmed is a status/evidence update, not automatically a fix.
