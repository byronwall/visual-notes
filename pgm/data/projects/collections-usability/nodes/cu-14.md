# CU-14 Preserve review position and support sequential record review

**Priority:** P2 · **Evidence:** Source verified capability gap; full navigation needs testing · **Baseline:** `25c7a864947994b8f321ceab73e6b8eae14e3107`

## Current behavior

CollectionPage keeps peekRowId in local component state; only the active view is in URL search parameters. RowPeekPanel renders one doc without next/previous controls or a position-in-view indicator. The 720px/full-viewport panel and note-body save guard already exist.

## User impact and gap

Reviewing a filtered batch requires repeated close/find/open actions. Opening a URL or reloading cannot restore the selected peek from the current route alone. Browser Back behavior and scroll retention need an authenticated end-to-end check.

## Reproduce

1. Filter a 110-row collection to a five-row batch; open row 3 and review it.
2. Move to the next record, use browser Back/Forward, follow a link, reload, close and reopen.
3. Test body and property edits during these transitions.

## Likely ideal and proposed work

Provide optional previous/next within the current result set, position/count, and a stable row URL or route state. Mobile detail should use full-width space and a clear return path; laptop detail should preserve enough collection context. Define what happens when an edit removes the item from the current filter.

## Acceptance and reassessment

- [ ] Returning restores view, filter, search, scroll and focus where promised.
- [ ] Next/previous follows the current filtered order and handles removed/reordered records explicitly.
- [ ] Unsaved work is protected across every navigation path, not only the close button.

Run R04 R08 R14 in the [reassessment protocol](../../../../../docs/intent/collections-usability-audit-2026-11-11/reassessment.md). Record fixed commit, browser/device, before/after screenshots and test result. A source hypothesis becoming confirmed is a status/evidence update, not automatically a fix.
