# CU-16 Separate editing a record from changing the collection schema

**Priority:** P2 · **Evidence:** Source verified design risk · **Baseline:** `25c7a864947994b8f321ceab73e6b8eae14e3107`

## Current behavior

PropertyList labels are property-settings buttons on a collection page, while values edit the current row. Table header menus similarly combine column/view configuration and schema operations. Embedded rows intentionally disable schema editing, which is a useful existing distinction.

## User impact and gap

A user trying to fill a record can instead enter schema settings that affect every record. The difference between local view visibility, global property changes and row values is not evident from a repeated label/value form alone.

## Reproduce

1. Open record detail and tap the property name rather than the value.
2. Compare Hide in view, rename property, change type and delete property entry points.
3. Repeat in embedded and standalone contexts using synthetic data.

## Likely ideal and proposed work

Keep row data entry primary. Put schema changes under a deliberate collection-level Edit properties action, or make the label settings affordance explicit. Label scope and retain conversion previews/confirmation for destructive schema changes.

## Acceptance and reassessment

- [ ] Record-entry controls cannot be mistaken for global schema changes.
- [ ] View-only versus collection-wide effects are stated before applying consequential changes.
- [ ] All schema operations remain available for power users without crowding routine review.

Run R15 in the [reassessment protocol](../../../../../docs/intent/collections-usability-audit-2026-11-11/reassessment.md). Record fixed commit, browser/device, before/after screenshots and test result. A source hypothesis becoming confirmed is a status/evidence update, not automatically a fix.
