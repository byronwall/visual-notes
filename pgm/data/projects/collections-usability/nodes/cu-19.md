# CU-19 Keep invalid numeric input visible with a clear error

**Priority:** P1 · **Evidence:** Source verified; browser follow-up required · **Baseline:** `25c7a864947994b8f321ceab73e6b8eae14e3107`

## Current behavior

ValueCell.finish closes the inline editor before parsing numeric text. It only saves when parseLooseText returns failed=false. The failed branch has no field error or retained visible draft. Existing stored values are not changed by this branch.

## User impact and gap

A mistyped number can appear to have been accepted when the editor closes, then silently revert to the old display. On a phone this is especially hard to distinguish from a missed save. This is a validation-feedback defect, not a claim of stored data corruption.

## Reproduce

1. In a numeric property enter a clearly invalid string, then press Enter.
2. Repeat by clicking outside and by tabbing to the next field.
3. Inspect the visible value and any error message, then attempt correction.

## Likely ideal and proposed work

Validate before closing, preserve the entered draft, and show an inline text error associated with the field. Keep Escape as an explicit cancellation path; only move focus after a successful commit or deliberate cancellation.

## Acceptance and reassessment

- [ ] Invalid numeric input remains available to correct with a textual explanation.
- [ ] No save success is implied when the value was rejected.
- [ ] Enter, blur and Tab have consistent validation behavior; Escape restores the previous value.

Run R08 R17 in the [reassessment protocol](../../../../../docs/intent/collections-usability-audit-2026-11-11/reassessment.md). Record fixed commit, browser/device, before/after screenshots and test result. A source hypothesis becoming confirmed is a status/evidence update, not automatically a fix.
