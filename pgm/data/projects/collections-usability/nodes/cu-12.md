# CU-12 Separate touch scrolling from drag-to-move gestures

**Priority:** P1 · **Evidence:** Source risk; real-device gesture test required · **Baseline:** `25c7a864947994b8f321ceab73e6b8eae14e3107`

## Current behavior

Board cards and calendar event/tray elements have touchAction:none. startPointerDrag begins after 5px movement and listens for pointermove/pointerup but not pointercancel. Property edits in detail offer an alternate way to change group/date, but manual ordering has no equally explicit non-drag control.

## User impact and gap

An ordinary swipe starting over a card can be interpreted as a move rather than scroll. Browser-interrupted pointer sequences may leave transient drag state. Source inspection does not establish the exact behavior on iOS/Android hardware.

## Reproduce

1. Swipe vertically and horizontally starting on card text, blank column space and calendar events.
2. Cancel an active drag via pointercancel, route change and Escape.
3. Try moving to another group/date and reordering with keyboard and without dragging.

## Likely ideal and proposed work

Use explicit drag handles or a deliberate press gesture that preserves native scrolling. Add Move to and position actions where order matters. Clean up every cancellation path and preserve the original value until drop is valid.

## Acceptance and reassessment

- [ ] Ordinary touch scroll never changes data.
- [ ] Canceled/interrupted drag restores card opacity, cursor, selection and pending state.
- [ ] All essential moves are possible without a drag gesture; touch hardware is included in proof.

Run R12 in the [reassessment protocol](../../../../../docs/intent/collections-usability-audit-2026-11-11/reassessment.md). Record fixed commit, browser/device, before/after screenshots and test result. A source hypothesis becoming confirmed is a status/evidence update, not automatically a fix.
