# CU-08 Explain when view changes are saved and recover failed saves

**Priority:** P2 · **Evidence:** Source verified; failure effects need integration test · **Baseline:** `25c7a864947994b8f321ceab73e6b8eae14e3107`

## Current behavior

Quick search is per view and per visit. Filter, sort, visible properties and widths patch the saved view after 400ms. Rename/layout/config failure paths show a toast but leave the locally changed view in place; no per-view pending/error state is exposed here.

## User impact and gap

Similar-looking controls have different persistence rules. A user can unintentionally change the saved view while exploring, or mistake a local unsaved configuration for a durable one. The actual server response and navigation timing need controlled integration tests.

## Reproduce

1. Search, change a filter, rename a view and change layout; reload after each.
2. Hold/fail updateView, then change view or reload.
3. Compare the displayed view state with the persisted server state.

## Likely ideal and proposed work

Choose explicit autosave-with-status and recovery, or temporary exploration with Save view/Reset. Label the active filter/sort context and show saving/saved/error where the user made the change. Provide retry or rollback rather than toast-only divergence.

## Acceptance and reassessment

- [ ] The UI communicates which changes persist and which are temporary.
- [ ] A failed save leaves a visible recoverable state and does not claim Saved.
- [ ] Fast successive view changes and route departure do not silently lose the latest intent.

Run R08 R09 in the [reassessment protocol](../../../../../docs/intent/collections-usability-audit-2026-11-11/reassessment.md). Record fixed commit, browser/device, before/after screenshots and test result. A source hypothesis becoming confirmed is a status/evidence update, not automatically a fix.
