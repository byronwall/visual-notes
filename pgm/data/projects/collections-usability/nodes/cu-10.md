# CU-10 Keep virtualized keyboard focus inside the table scroller

**Priority:** P1 · **Evidence:** Source risk; large-data browser test required · **Baseline:** `25c7a864947994b8f321ceab73e6b8eae14e3107`

## Current behavior

Rows above 150 use fixed-height windowing. Collection pages now have an internal scroll container, but useWindowedRows.reveal scrolls window with window.scrollBy. focusCell then queries the requested cell after one microtask.

## User impact and gap

Arrow navigation toward an off-window row may scroll the wrong ancestor or target a row that has not rendered. An invisible or lost focus disrupts laptop work and assistive technology. Ordinary scroll handling captures ancestor events, so this is specifically a reveal/focus path to test.

## Reproduce

1. Load 300 and 2,000 synthetic rows.
2. Arrow down from the last visible row repeatedly inside the nested table scroller.
3. Repeat after page scroll, filtering from 2,000 rows to 5, opening detail and returning.

## Likely ideal and proposed work

Measure and scroll the actual owning container; render/reveal the target row before moving focus. Preserve stable row identity through filtering and virtualization. Add an integrated keyboard regression.

## Acceptance and reassessment

- [ ] Focused row is rendered, visible and not covered by sticky headers or footer.
- [ ] Page scroll does not jump unexpectedly during table-only keyboard navigation.
- [ ] Focus remains stable across window boundaries and large-to-small filtered results.

Run R05 R10 in the [reassessment protocol](../../../../../docs/intent/collections-usability-audit-2026-11-11/reassessment.md). Record fixed commit, browser/device, before/after screenshots and test result. A source hypothesis becoming confirmed is a status/evidence update, not automatically a fix.
