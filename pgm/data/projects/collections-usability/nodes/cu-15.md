# CU-15 Make result counts and empty states explain what happened

**Priority:** P2 · **Evidence:** Source verified; browser follow-up required · **Baseline:** `25c7a864947994b8f321ceab73e6b8eae14e3107`

## Current behavior

The page header reports total rows. The table footer can count filtered rows, but no matching rows shows only No rows match this view plus New. Gallery renders the New card for zero results; board/calendar retain layout structures without an equivalent clear shared no-results recovery. Search is separate from saved filters.

## User impact and gap

A user can misread an empty filter or missing date as data loss, especially when the total count is above a large view toolbar. Recovery requires guessing which control hid the records.

## Reproduce

1. Compare a new empty collection, no search matches, no filter matches, an empty group and all-undated calendar.
2. Apply both search and filter, then clear only one.
3. Inspect counts above/below the fold at 390 and 1280px.

## Likely ideal and proposed work

Use visible result counts such as 5 of 110 and distinct empty/loading/error/no-results states. Show active constraints with Clear search/Reset filters actions, preserving saved-view semantics. Explain undated/hidden group exclusions.

## Acceptance and reassessment

- [ ] The user can distinguish no data from hidden data without opening settings.
- [ ] A one-action recovery returns to visible records without deleting a saved view.
- [ ] Counts agree across table, board, gallery, calendar and detail navigation.

Run R09 R13 in the [reassessment protocol](../../../../../docs/intent/collections-usability-audit-2026-11-11/reassessment.md). Record fixed commit, browser/device, before/after screenshots and test result. A source hypothesis becoming confirmed is a status/evidence update, not automatically a fix.
